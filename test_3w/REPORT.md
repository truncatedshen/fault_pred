# 3W 真实故障数据 · test_3w 工作空间报告

用 fault-prediction MCP 会话 + `fault-prediction` skill,在巴西石油( Petrobras)公开的
**3W 数据集**上跑通了一条真实的设备异常检测流水线。结论先说:**合成数据上的 1.000 在真实数据上
掉到 0.56–0.67**,这才是可信的基线。

## 数据来源

| 项目 | 内容 |
| --- | --- |
| 数据集 | 3W Dataset v2.0.0,Petrobras,CC BY 4.0 |
| 来源 | `github.com/petrobras/3W` 的 `dataset/` 目录(Parquet,共 1.74 GB) |
| 内容 | 真实海上油井多变量时序,每 1 秒一行,27 个过程变量 |
| 类别 | 10 类:`0` 正常,`1`–`9` 故障(BSW 突增、DHSV 误关、严重段塞流、流动不稳定、产能骤降、PCK 快速堵塞、PCK 结垢、生产管线水合物、服务管线水合物) |
| 来源标记 | 文件名前缀区分 `WELL-*`(真实)、`SIMULATED_*`、`DRAWN_*`;**本工作只取真实实例** |

取数只下载需要的文件(全库 1.74 GB):先从每类取少量真实实例做画像,再按质量筛选补下载,
最终下载 61 个实例、72.9 MB,选用其中 28 个。

## 真实数据的三处硬约束

这些是合成数据不会暴露、但真实工况一定会遇到的问题,也是本次最主要的发现。

**一、标签有三段结构,而且开头有一段未标注。**
每个实例的时间轴是 `未标注(前 1 小时) → 正常(0) → 前兆(1xx) → 真实故障(x)`。
未标注的 3600 行全部丢弃;前兆标签(`101`–`109`)按 `class % 100` 归到对应故障类型,
并在二分类里计入异常。产出列:`label`(事件类型 0–9)、`phase`(0 正常 / 1 前兆 / 2 故障)、
`fault`(0/1,本次建模目标)。

**二、传感器可用性按井而变,而且"有值"不等于"有效"。**
这是最要命的一条。在 61 个实例上逐列统计:

| 列 | 有效(非常数) | 整列缺失 | **恒为 0** |
| --- | --- | --- | --- |
| `P-MON-CKP` | 44 | 17 | 0 |
| `P-TPT` | 52 | 5 | 4 |
| `T-TPT` | 54 | 6 | 1 |
| `P-JUS-CKGL` | 35 | 25 | 1 |
| `P-PDG` | 29 | 9 | **23** |
| `T-PDG` | 29 | 17 | **15** |

`P-PDG` 在 61 个实例里有 23 个恒为 0——传感器未投用,历史库用 0 填充。第一版筛选只检查
"非空",把这些 0 当成有效值放进流水线,结果频域组件直接报错;更隐蔽的是,这种列会让模型
学出"某列为 0 ⟶ 某口井"的捷径。

最终核心传感器取 `P-MON-CKP`、`P-TPT`、`T-TPT`——要求"非缺失且非常数"时,它们是能同时覆盖
**全部 10 个类别**的最宽组合(28 个实例、14 口井)。缺失值只在实例内部前向/后向填补
(间隙是秒级),整列无效的实例直接剔除而不是插补。

**三、点位是量化 + 保持值,窗口内可能完全平直。**
`T-TPT` 在 180 秒窗口里有 7.8% 完全恒定,`P-TPT` 高达 19.4%,`P-MON-CKP` 0.4%。

## 数据集构建

| 项目 | 值 |
| --- | --- |
| 实例 / 井 | 28 / 14 |
| 行数 | 489,456(1 Hz) |
| 列 | `instance`, `time_s`, `label`, `fault`, `phase`, `state` + 3 个传感器 |
| 每类实例数 | 0:4, 1:3, 2:3, 3:3, 4:3, 5:2, 6:2, 7:3, 8:3, 9:2 —— **10 类全覆盖** |
| 文件 | `test_3w/data/3w_events.parquet`(3.0 MB) |

每个实例裁剪为"事件前 3 小时正常段 + 前 3 小时前兆 + 事件前 4 小时",既保住因果顺序,
又把产物控制在可处理规模。脚本:`test_3w/prepare_dataset.py`(可重跑,分
`inventory` / `download` / `topup` / `build` 四个阶段)。

## 结果

| 模型 | Accuracy | Precision | Recall | F1 | ROC-AUC | 正常类召回 | 故障类召回 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Random Forest (n=300) | **0.6660** | 0.6639 | 0.6660 | **0.6606** | 0.7082 | 0.5334 | 0.7713 |
| SVM (rbf, C=10) | 0.5624 | 0.5476 | 0.5624 | 0.4857 | 0.6784 | 0.1408 | 0.8975 |
| XGBoost (n=300, depth=4) | 0.5888 | 0.5822 | 0.5888 | 0.5623 | **0.7372** | 0.3198 | 0.8027 |

测试集 1,892 个窗口(正常 838 / 异常 1,054),混淆矩阵:

```
Random Forest [[447, 391], [241, 813]]
SVM           [[118, 720], [108, 946]]     <- 几乎全判成故障
XGBoost       [[268, 570], [208, 846]]
```

对照上一轮合成数据的 1.000/1.000/1.000,真实数据上的差距就是这次测试的价值。

### 结果怎么读

1. **RF 最均衡,但远谈不上好用。** 66.6% 准确率意味着每三个窗口错一个;正常类召回只有
   53%,近一半的正常工况会被误报。
2. **SVM 退化了。** 正常类召回 0.14——它基本在无脑预测"故障"。这暴露的是类别代价不对称:
   在故障预警场景里,漏报比误报严重,但"全报故障"显然没有工程价值,必须看召回而不是准确率。
3. **XGBoost 的 AUC 最高(0.737)但阈值化后最差之一**,说明它的排序有信息量,只是被不均衡
   数据推到了偏向多数类的阈值。XGBoost 在这个任务上也跑了约 5 分钟,比 RF/SVM 慢一个量级。
4. **测试实例 = 7 个,来自 7 口不同的井。** 其中 WELL-00009、WELL-00016、WELL-00021、
   WELL-00027 在训练集里**完全没出现过**,所以这不是纯记忆题;但 WELL-00001、WELL-00003、
   WELL-00014 同时出现在训练集,这 3 个测试实例属于"同井不同事件"。
   因此 0.666 是**同井泛化与跨井泛化的混合**,不是严格的留一井评估。

## 平台的三个使用限制

这次踩到的、建议在上游修掉的问题:

1. **`feature.spectral` 遇到平窗口直接抛 `ValueError: Spectral features need a signal with
   non-zero variance`,整个流水线失败。** 真实过程数据里量化/保持值点位必然产生平窗口(本例
   `P-TPT` 19.4%),这是常态而非异常输入。建议改为该窗口输出 NaN 或跳过该列,而不是中断执行。
   本次因此移除了频域分支——1 Hz 采样率已知,但组件用不了。
2. **`label_policy=strict` 在窗口跨越标签边界时报错**,而故障起始点恰恰是这类任务最关心的地方。
   改为 `mode` 可解,但默认值对时序故障检测并不友好。
3. **`GET /api/data` 只列出 `.csv`**,Parquet 文件不会出现在列表里(上传/数据集浏览界面因此
   看不到它们),但 `data.input` 读取 `.parquet` 是正常的。

## 复现

```
# 1. 取数 + 构建数据集(可重复执行,已下载文件会跳过)
python test_3w/prepare_dataset.py all

# 2. 服务必须以本工作空间为数据根目录
python -m fault_platform serve --port 8765 \
  --data-root test_3w/data \
  --storage-root test_3w/.fault-platform/pipelines --artifact-cache-mb 1024

# 3. 无界面复算并打印精简指标(准确率、混淆矩阵、每类召回、测试井是否见过)
```

## 下一步建议(按收益排序)

1. **严格留一井评估。** 每个井只保留一个实例,让 group 划分等价于按井划分,才能回答"新井能不能
   用"这个真正的问题。当前 28 个实例里同一口井最多有 5 个实例。
2. **修好 `feature.spectral` 后补频域特征。** 段塞流是振荡现象,频域特征在物理上比统计量更对口;
   1 Hz 采样、180 秒窗口的频率分辨率约 5.6 mHz,足以覆盖分钟级的段塞周期。
3. **引入 3W 官方训练/测试划分**,与已发表结果可比。
4. **多类事件识别**(10 类),但类别 5/6/9 的真实实例偏少,需要先解决样本量。
5. **代价敏感评估**:以漏报率为主指标而不是准确率,并给出 PR 曲线而不是单点阈值。
