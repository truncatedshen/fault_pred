你是一名资深 Python 架构师、机器学习工程师、工业故障预测专家和可视化低代码平台设计专家。

我要开发一个“故障预测组件化建模平台”。

它的设计思想类似 Simulink：

用户不是直接编写完整故障预测代码，而是通过一系列最小粒度的“原子功能模块”，以拖拽、配置参数、连接模块的方式搭建完整的数据分析、特征工程和故障预测方案。

注意：

这里的“组件”不是 MCP Tool。

组件是故障预测领域内部真正执行计算的原子功能模块。

MCP 和 Skill 只是未来让外部 AI Agent 操作这个组件系统的接口层。

整个系统核心应该是：

原子组件
+
组件连接
+
数据流
+
XML方案描述
+
执行引擎
+
可视化编辑器

==================================================
二十二、核心设计原则
==================================================

始终遵循：

1. Component 是最核心抽象。

2. 一个 Component 应尽量只完成一种原子能力。

3. Component 之间只通过 Port 交换数据。

4. Graph 决定组件连接关系。

5. XML 描述 Graph。

6. Workspace 保存真实运行数据。

7. XML 不保存大型运行数据。

8. ExecutionEngine 负责执行 Graph。

9. Visualizer 只是 Graph 的图形化编辑器。

10. MCP 是 Agent 操作 Graph 的接口。

11. Skill 是 Agent 搭建故障预测 Graph 的专业知识。

12. Component 不应该知道 LLM、MCP 或 Skill 的存在。

13. 新增 Component 不应要求修改执行引擎。

14. 参数 UI 应由 Parameter Schema 自动生成。

15. Port 必须进行类型校验。

16. Graph 必须进行合法性校验。

17. 所有方案必须可以序列化为 XML。

18. XML 必须能够重新完整恢复 Graph。

二十三、最终产品定位
==================================================

最终产品不是：

“一个故障预测模型”。

也不是：

“一堆 MCP Tools”。

而是：

“一个面向故障预测的组件化建模与执行平台”。

类似：

Simulink
+
故障预测原子能力库
+
可视化 Pipeline Designer
+
XML 方案描述
+
Agent MCP 控制接口
+
Fault Prediction Skill

用户可以手工拖拽组件搭建方案。

AI Agent 也可以通过 MCP 自动搭建完全相同的方案。

无论人工还是 Agent 创建方案，

最终都转换成统一的：

ComponentGraph

并可以保存为：

XML。

请优先把 Component / Port / Graph / XML / Execution Engine 这五个核心抽象设计正确，再开始实现 UI、MCP 和 Skill。
